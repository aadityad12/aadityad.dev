Project 01 · Embedded vision · Infineon

VisionAssist

Obstacle warnings you can hear, with no phone or internet.

The project /A head-mounted Raspberry Pi 5 and camera that spot obstacles, estimate how far away they are, and say so through Bluetooth earbuds. Everything runs on the device. A team of five built it through De Anza's ENGR 77 course with Infineon, and we demoed it to Infineon's sponsors in June 2026.

My part /I was the software lead. I built the pipeline from camera capture to YOLOv8n detection (about 200 ms a frame on the Pi's CPU), distance estimates from bounding-box height, and offline speech that announces only the riskiest, closest object, in feet and steps. It boots headless as a systemd service, with a phone web app as a second output.

What didn't work /We were asked to use Infineon's 60 GHz radar. Close-range readings were dominated by antenna leakage and floor reflections, and fusing radar with the camera would have needed 3D localization we couldn't build in one quarter. After several weeks I cut it and wrote up why for Infineon. The distance estimate still overshoots inside about four feet, and the repo says so.

Python · YOLOv8 · OpenCV · Picamera2 · Flask · Piper TTS · Raspberry Pi 5

Project 02 · Languages · C++ and ARM64

Rung

One tiny language, five engines, every speed-up measured.

The project /Every explanation of how Python, Lua, or JavaScript get fast lists the same tricks: bytecode, register machines, smaller values, JITs. I wanted to know how much each one actually helps, so I built a tiny language and implemented it five times: a tree-walking interpreter, a stack VM, a register VM, an ARM64 JIT, and a JIT that compiles on a background thread. All five have to print byte-identical output.

What I found /The stack VM ran 1.30x to 4.99x faster than the tree-walker, and the JIT reached 22.64x on the one benchmark where a function compiles. NaN-boxing halved the size of every value and still made every benchmark slower. I don't know why yet, so it stays in the table. The JIT's ARM64 encoder is hand-written and checked byte for byte against LLVM's assembler.

Testing /Sanitizers, a fuzzer, and CI on macOS and Linux across ARM64 and x86-64. Looping the tests hundreds of times in CI exposed a crash in about 5% of runs: UBSan reads 8 bytes before the target of an indirect call, and JIT code at the very start of a page made that read hit unmapped memory. Sixteen zero bytes fixed it.

C++20 · ARM64 · CMake · libFuzzer · ASan / UBSan / TSan · GitHub Actions

Project 03 · AI developer tools

Accordion

See what your coding agent remembers.

The project /When a coding agent's context fills up, most tools squash the session into one lossy summary. Accordion shows the context as a map instead, and lets you or the agent fold, unfold, or pin individual blocks. Folding only changes what the agent sees, so nothing is lost. Built by Tyler Darisme, Sheel Shah, Thy Tang, and me, it won The Token Company sponsor track at the UC Berkeley AI Hackathon 2026. In the team's hackathon-scale SlopCodeBench run, its Thermocline conductor finished 5 of 6 checkpoints, against 2 of 6 for naive compaction.

My part /Through June 2026 I worked on the conductor, the part that decides what to fold. I built a way to tell whether folding was helping: health metrics, evaluators, and a harness that compares a session against naive compaction. I added a cross-encoder rerank stage for choosing what to unfold, ported the conductor onto Accordion's command contract (PRs #68 and #71), and built a dashboard showing the conductor's health and each decision it made.

My part: TypeScript · Hugging Face Transformers · SvelteKit

Project 04 · Automation · Security design

OSS Scout

Finds open-source work every night. Posts nothing without me.

The project /Maintainers are buried in low-effort, machine-generated pull requests. OSS Scout automates the tedious parts of contributing (finding good issues, judging how welcoming a project is to outside contributors, reading unfamiliar code) and leaves the decisions to me. Each night it scans GitHub, prepares at most one tested draft fix, and emails me a summary in the morning. Nothing is posted until I approve it.

How it stays safe /The AI routine that prepares fixes can't write to GitHub at all: a guard hook blocks every write command, with 37 tests behind it. The only write token lives in a separate private repo the routine never sees, and a single workflow does all the posting after re-checking each item. Text from strangers' issues is treated as data, not instructions.

Python · GitHub Actions · Claude Code hooks · Cloudflare Workers and Access

Project 06 · On-device ML · Android

GazeBoard

Talking by looking, with nothing leaving the phone.

The project /A communication board for people who can't speak or use their hands. The front camera finds the face, crops one eye, and Qualcomm's EyeGaze model estimates where the person is looking. Holding their gaze on one of four tiles for a second selects it, and the phone speaks it. Because the camera points at someone's face all day, the app asks for camera access and nothing else, not even the internet.

My part /I worked across the path from camera capture through calibration to speech output, and I owned the inference path: the model runs only on the phone's NPU, and if the NPU fails to load, the app says so instead of quietly falling back. I also built the debug overlay and the recalibration flow, trimmed the spelling vocabulary to 378 words, fixed the Gradle build, and later rewrote the docs. Built at the Qualcomm × Google LiteRT Developer Hackathon with Sheel Shah and Nishanth Nagesh.

Kotlin · Compose · CameraX · ML Kit · LiteRT · Hexagon NPU

  • On-device
  • Camera permission only
  • Apache-2.0

Echo

Emergency alerts that keep moving when the internet doesn't.

Project 08 · AI evaluation

Temper

Test the system around the model.

The project /A model's system prompt, skills, and tools can quietly make it worse. Temper asks the same questions with and without that harness; if the harness scores lower, the harness is the cause. It then writes replacement files for the parts that failed and re-checks only those.

My part /I wrote the spec, API contract, and JSON Schemas, and built the local client, the pi extension, and the FastAPI service (Gemini as judge, DeepSeek as the bare baseline, and the patch generator). I also wrote a deliberately flawed customer-support agent with an answer key, so the whole evaluate, patch, re-evaluate loop runs offline with no API keys. That offline path is tested; the live-model path isn't currently verified. Built at the AI Engineer World's Fair Hackathon 2026 with Sheel Shah.

Python · FastAPI · JSON Schema · Gemini · DeepSeek
